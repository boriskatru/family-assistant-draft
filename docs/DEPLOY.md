# Развёртывание на VPS

## 1. Подготовка

Рекомендуемый старт — Ubuntu 24.04 LTS x86_64/arm64, 2 vCPU, 4 ГБ RAM, SSD от 40 ГБ. Сервер должен иметь исходящий HTTPS-доступ к Telegram, Google и выбранному LLM API. Для установки нужны также репозитории Docker и Python. ИИ-модель работает через API; GPU на VPS не требуется.

Распакуйте архив и перейдите в `family-assistant`. Все команды ниже запускайте из этого каталога под root либо пользователем с доступом к Docker. Установка через sudo сама по себе не выдаёт пользователю доступ к Docker: если он требуется, выполняйте команды `docker` с sudo, а скрипты резервирования — через `sudo bash`. Вспомогательный установщик поддерживает Ubuntu и не удаляет существующие контейнеры или пакеты автоматически:

```bash
sudo bash scripts/install_docker_ubuntu.sh
docker compose version
python3 scripts/generate_env.py
nano .env
```

Если Docker установлен другим способом и helper сообщает о конфликтующих пакетах, выполните установку по [официальной инструкции Docker](https://docs.docker.com/engine/install/ubuntu/). Не удаляйте старую установку, пока не проверите, какие сервисы её используют.

## 2. Telegram и минимальные настройки

1. Создайте бота через [BotFather](https://t.me/BotFather), поместите токен в `TELEGRAM_BOT_TOKEN`.
2. Укажите два числовых Telegram ID в `ALLOWED_TELEGRAM_IDS`, например `123456789,987654321`. Имена — `USER_NAMES=Борис,Анна`. ID определяет аккаунт, имя используется для отображения.
3. `SHARED_CHAT_ID` оставьте пустым для личных чатов; позднее можно вписать числовой ID закрытой семейной группы. В группе должны состоять только вы двое: бот отказывает командам посторонних, но любой участник группы видит уже отправленные в неё сообщения.
4. Сохраните `.env` с правами `600`. `generate_env.py` откажется перезаписывать существующий файл.

Секреты PostgreSQL, Django, webhook и ключ шифрования уже сгенерированы. Не копируйте `.env` в Git. Переменная `DATABASE_URL` задаётся Compose внутри контейнеров; её не нужно заполнять вручную. Значение `POSTGRES_PASSWORD` генерируется в формате, безопасном для URL.

```bash
docker compose up -d --build
docker compose ps
docker compose logs --tail=80 migrate bot worker_chat worker_service worker_notifications scheduler
```

`migrate` завершится с кодом 0 — это нормальное состояние одноразовой службы. Остальные процессы должны работать. PostgreSQL и файлы не публикуются на портах VPS. Каждый отправляет боту `/start`, затем `/help`; для получения собственного ID есть `/id`.

Если ID ещё неизвестны, начните с пустого списка и получите `/id`, затем добавьте оба ID и повторите запуск/инициализацию:

```bash
docker compose run --rm migrate
docker compose up -d --force-recreate bot worker_chat worker_service worker_notifications scheduler
```

Этот способ предполагает, что пустой список разрешений закрывает доступ ко всем данным; исключение — ответ `/id` о собственном аккаунте.

Если после обновления бот молчит, отправьте в личном чате **новую** команду `/id`. Ответ с предложением добавить ID означает, что сообщение прошло через Telegram и обе очереди, а доступ к расписанию ещё закрыт. Проверьте `ALLOWED_TELEGRAM_IDS` и выполните команды инициализации выше. Если ответа нет, посмотрите `docker compose logs --since=5m --tail=60 bot worker_chat worker_notifications`. В версии с исправлением polling уже завершённые запросы повторно не выполняются.

Повторяющаяся строка `Polling retry: PydanticSerializationError` встречалась в предыдущей версии при получении сообщений с предпросмотром ссылки. После обновления исходников выполните `docker compose build bot && docker compose up -d --no-deps bot`. Бот продолжит забирать ожидающие сообщения. Для проверки отправьте `/id`. В новых строках `Polling retry` указаны этап обработки, номер обновления и тип ошибки.

## 3. Агент, свободный текст, голос и документы

Первые команды можно проверить без ИИ. Для естественного языка заполните:

```dotenv
LLM_API_KEY=ваш_ключ
LLM_MODEL=gpt-6-luna
LLM_BASE_URL=https://api.openai.com/v1
LLM_REASONING_EFFORT=
LLM_PROMPT_CACHE_TTL=30m
AGENT_ENABLED=1
AGENT_AUTONOMY=personal
AGENT_HISTORY_USER_LIMIT=50
```

Модель должна поддерживать Responses API с function tools. В примере используется GPT-6 Luna. Для Terra укажите `LLM_MODEL=gpt-6.1-terra`. Пустой `LLM_REASONING_EFFORT` оставляет выбор усилия рассуждения поставщику модели. Чтобы задать усилие основного агента явно, например для Luna или Terra, укажите `LLM_REASONING_EFFORT=low`, `medium` или `high`.

При `AGENT_HISTORY_USER_LIMIT=50` агент видит текущий запрос и до 49 предыдущих текстовых или расшифрованных голосовых сообщений пользователя в том же чате вместе с ответами. История сохраняется в PostgreSQL. Для более короткого окна задайте целое число от 1 до 50. В общем чате у каждого отправителя своя история. Перед повторным использованием текста агент проверяет доступ к связанным записям.

В длинном разговоре агент резервирует место для текущего запроса и ответа, затем добавляет свежие вопросы вместе с ответами. Если токенного бюджета мало, старые пары целиком выпадают из запроса к модели. Команда `/agent_history` в личном чате показывает общее число входных токенов и сколько из них провайдер прочитал из кэша.

При прямом подключении GPT-6 Luna или GPT-6.1 Terra к OpenAI `LLM_PROMPT_CACHE_TTL=30m` задаёт минимальный срок хранения кэша общей начальной части запросов на стороне провайдера. Доступен также `12h` с более высокой ценой записи. Фактические попадания зависят от совпадения начала запроса и доступности кэша. Количество прочитанных из кэша токенов сохраняется в `AgentRun.usage.cached_input_tokens`. [Кэширование запросов OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching).

`AGENT_ENABLED=1` включает многошаговый цикл OpenAI Agents SDK. В режиме `personal` агент сам выбирает инструменты и выполняет разрешённые операции; для нового события на двоих достаточно запроса одного участника. Режим `read_only` разрешает поиск, чтение, расчёт черновика плана и выдачу доступных файлов в текущий чат, но запрещает агенту изменять задачи/события и принимать план с записью блоков расписания. Режим конкретного пользователя меняется в его личном чате: `/agent autonomy read_only` или `/agent autonomy personal`. `/agent` показывает настройки. Явные команды `/event`, `/task` и другие остаются самостоятельными командами пользователя.

`AGENT_ENABLED=0` возвращает прежний одношаговый обработчик с подтверждением каждого предложенного ИИ изменения. Сохранённые напоминания и планировщик работают независимо от обоих режимов.

Лимиты одного запуска:

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `AGENT_MAX_TURNS` | 12 | Максимум обращений основного цикла к модели |
| `AGENT_MAX_TOOL_CALLS` | 24 | Максимум вызовов инструментов |
| `AGENT_MAX_EXTERNAL_CALLS` | 8 | Максимум внешних инструментов: поиск, страницы, карты |
| `AGENT_TIMEOUT_SECONDS` | 180 | Срок остановки цикла; уже начатая операция завершается перед отчётом |
| `AGENT_MAX_OUTPUT_TOKENS` | 2000 | Максимальный вывод одного ответа основной модели |
| `AGENT_MAX_TOTAL_TOKENS` | 80000 | Бюджет входных и выходных токенов на весь запуск, включая учтённые токены встроенного веб-поиска |
| `LLM_WEB_SEARCH_MAX_OUTPUT_TOKENS` | 1800 | Максимальный вывод отдельного запроса встроенного веб-поиска |
| `LLM_STRUCTURED_MAX_OUTPUT_TOKENS` | 4000 | Максимальный вывод отдельного структурированного ответа при разборе документа или в одношаговом обработчике |

Числовые бюджеты проверяются при запуске. Перед запросом агент оценивает размер контекста и уменьшает допустимый вывод до остатка общего бюджета. Кэшированные токены уже учтены во входных. На стоимость также влияют тарифы карт и поиска. При достижении лимита агент сообщает, какие действия успел сохранить.

Опциональные `LLM_TRANSCRIPTION_MODEL` и `LLM_DOCUMENT_MODEL` включают распознавание голоса и изображений/документов. При пустых значениях соответствующая удалённая обработка отключена. PDF с текстовым слоем обрабатывается локально; сканы требуют модели документов. Содержимое выбранных сообщений и файлов передаётся настроенному поставщику API.

После изменения `.env`:

```bash
docker compose up -d --force-recreate bot worker_chat worker_service worker_notifications scheduler
```

### Интернет и карты

Для веб-поиска по умолчанию используется native web search OpenAI с `LLM_API_KEY`. При необходимости задайте отдельную поддерживающую web search модель в `LLM_WEB_SEARCH_MODEL`; пустое значение использует `LLM_MODEL`. Совместимость обычных function tools не гарантирует поддержку встроенного web search у другого провайдера.

Альтернативный поисковый провайдер — Brave Search API: заполните `BRAVE_SEARCH_API_KEY`, и инструмент поиска будет обращаться к Brave. Для чтения найденных публичных страниц отдельный ключ не нужен. Бот читает ограниченный объём доступного HTTP-контента; JavaScript-приложения, страницы за входом и платным доступом он не открывает как браузер.

Для мест и маршрутов:

1. В Google Cloud подключите Google Maps Platform и биллинг.
2. Включите **Places API (New)** и **Routes API**.
3. Создайте отдельный серверный API key, ограничьте его этими API и, если VPS имеет постоянный исходящий IP, этим IP.
4. Добавьте ключ в `GOOGLE_MAPS_API_KEY` и пересоздайте службы приложения.

Google Maps key не заменяет OAuth-ключи Calendar. Для серверного поиска мест и маршрутов публичный домен не требуется. Поддержаны автомобиль, пеший путь, велосипед и общественный транспорт; для автомобиля запрашивается время с учётом трафика. Оценки пути зависят от покрытия и ответа провайдера; при ошибке или отсутствии ключа агент сообщит об этом, а не придумает длительность. Информация о фактических задержках авиарейсов отдельным API не подключена.

Веб-запросы передают поисковую фразу провайдеру поиска, запросы карт — адреса/координаты Google. Содержимое полученных страниц, документов и записей воспринимается как данные; доступ к инструментам и записям ограничен приложением.

## 4. Google Calendar и Meet

Для Google нужен публичный HTTPS callback. Домен используется для служебного адреса; веб-интерфейса у приложения нет.

1. Создайте DNS A-запись поддомена, например `assistant.example.org`, на IPv4 VPS. Если используете AAAA, она также должна вести на этот сервер. Откройте входящие TCP 80/443 в firewall хостинга; не публикуйте PostgreSQL.
2. В Google Cloud создайте проект, включите **Google Calendar API**, настройте OAuth consent screen, создайте OAuth client типа **Web application**.
3. Добавьте точный authorized redirect URI: `https://assistant.example.org/oauth/google/callback/`.
4. Для тестового режима добавьте оба Google-аккаунта в test users. У внешнего приложения со статусом Testing refresh tokens для Calendar выдаются на 7 дней: потребуется переподключение; настройку долгосрочной публикации OAuth проверьте по [правилам Google](https://developers.google.com/identity/protocols/oauth2#expiration).
5. Заполните `.env`:

```dotenv
PUBLIC_HOST=assistant.example.org
PUBLIC_BASE_URL=https://assistant.example.org
ALLOWED_HOSTS=assistant.example.org,localhost,127.0.0.1
GOOGLE_CLIENT_ID=...
GOOGLE_CLIENT_SECRET=...
GOOGLE_REDIRECT_URI=https://assistant.example.org/oauth/google/callback/
```

```bash
docker compose --profile web up -d --build
docker compose logs --tail=80 app caddy
```

Caddy получает и продлевает сертификат при корректных DNS и доступных 80/443. Если на этих портах уже работает другой reverse proxy, используйте его вместо Caddy и направьте запросы на контейнер приложения; не запускайте два proxy на одних портах.

Каждый пользователь в **личном** чате выполняет `/google`, проходит авторизацию, затем `/calendars` и `/calendar ID_календаря | personal | rw`. Для общего календаря используется `shared` вместо `personal`; `ro` подключает источник только для чтения. В черновике запрашивается доступ Calendar; Gmail не подключается. Личный календарь должен быть закрыт от других людей также в настройках самого Google. Общий календарь подключается на запись один раз; события с личной видимостью в него не экспортируются. Для экспорта используется первый доступный для записи личный источник.

Google Meet создаётся только если подключённый календарь и аккаунт поддерживают эту возможность. Произвольная ссылка на другой сервис может храниться в событии. Особенности синхронизации серий и конфликтов описаны в [STATUS.md](STATUS.md).

При обнаруженном двустороннем конфликте владелец выбирает `/resolve ID_события local` или `/resolve ID_события remote`. Сначала прочитайте обе версии в сообщении бота: выбранная станет актуальной.

## 5. Проверка перед использованием

1. Оба пользователя получают `/start` и `/help`, посторонний — отказ доступа.
2. Создайте личное событие через команду из `/help`; второй пользователь не должен видеть его подробности.
3. Добавьте событию список вещей, отметьте пункт и повторно откройте список.
4. Создайте напоминание на ближайшее время; проверьте доставку в личный чат.
5. Перезапустите процессы: `docker compose restart`; убедитесь, что данные и отметки сохранились.
6. После Google-подключения проверьте создание, ручной перенос из Google и получение Meet.
7. В личном чате выполните `/agent autonomy read_only`, попросите найти свободное окно и прочитать загруженный документ: агент должен использовать данные без изменений.
8. Верните `/agent autonomy personal`, попросите создать личное событие; проверьте карточку и журнал `/agent_history`. Попросите добавить спектакль на двоих. Сразу откройте план на эту дату в обоих личных чатах и проверьте время. Затем повторите проверку с другого аккаунта для нового события.
9. Попросите найти официальный сайт места и построить маршрут. Проверьте ссылки, источник времени пути и понятное сообщение при отключённом API.

Код и тесты включены, но работоспособность конкретных аккаунтов/API и сетевого доступа подтверждается этой проверкой на вашем VPS. Время на устройстве пользователя зависит и от Telegram/связи.

### Фото или документ с подписью

В личном чате перешлите сообщение с фото или документом и подписью. В ответе появится «Текст подписи сохранён полностью». Откройте присланную команду `/show document ID` или спросите «Когда начинается спектакль на этой афише?». Подпись хранится отдельно от распознанных сведений, включая переносы строк. Сохранение работает без ключа ИИ.

После обновления со старой версии можно проверить, сохранилось ли исходное сообщение в журнале, и восстановить подписи к личным документам:

```bash
docker compose exec worker_chat python manage.py backfill_telegram_captions
docker compose exec worker_chat python manage.py backfill_telegram_captions --apply
```

Первая команда показывает число подходящих документов (`eligible`), вторая записывает подписи и выводит число восстановленных (`applied`). Общие документы, неоднозначные совпадения и уже заполненные подписи пропускаются. Если старая подпись отсутствует после восстановления, перешлите боту исходное сообщение ещё раз.

## 6. Обновление и остановка

После обновления любой из двух участников может сразу добавить событие для обоих. Если в старой версии остались будущие события с действующим запросом на подтверждение создания, проверьте их количество:

```bash
docker compose exec worker_chat python manage.py activate_joint_events
```

Чтобы применить новое правило к этим событиям, повторите команду с `--apply`. Команда активирует только общие события, в которых участвуют оба разрешённых пользователя и с момента запроса не менялись детали. Для переноса и отмены действуют отдельные согласования.

Перед обновлением сделайте резервную копию. Сохраните предыдущую версию кода и `.env`, замените исходники. При переходе с первого черновика добавьте новые `AGENT_*`, `LLM_WEB_SEARCH_MODEL`, `BRAVE_SEARCH_API_KEY` и `GOOGLE_MAPS_API_KEY` из `.env.example` по необходимости; существующие секреты сохраняются. Не запускайте генератор поверх рабочего `.env`.

Миграция `0002` добавляет журнал запусков агента и результатов инструментов. Применить её нужно до запуска новых workers:


```bash
docker compose build
docker compose stop bot worker_chat worker_service worker_notifications scheduler
# Если профиль web уже запущен: docker compose --profile web stop app
docker compose run --rm migrate
docker compose up -d
# Если Google HTTPS включён:
docker compose --profile web up -d
```

Остановка с сохранением данных: `docker compose down`. Команда `docker compose down -v` удаляет volumes с БД и билетами — для обычного обновления она не нужна. Откат кода после изменения схемы БД требует совместимой миграции либо восстановления резервной копии.

Состояние и последние логи:

```bash
docker compose ps
docker compose logs --tail=100 worker_notifications worker_service
```

## 7. Резервирование и восстановление

Архив резервирования содержит PostgreSQL, загруженные файлы и `.env` с ключом шифрования. Он шифруется через `age`. Ключ расшифровки храните отдельно от VPS и от самих копий.

Установите `age`, создайте ключ на доверенном компьютере:

```bash
age-keygen -o family-backup-key.txt
age-keygen -y family-backup-key.txt
```

Вторая команда показывает публичного получателя `age1...`. На VPS нужен только он, а не приватный ключ:

```bash
sudo apt install age
bash scripts/backup.sh /secure/backups age1ВАШ_ПУБЛИЧНЫЙ_ПОЛУЧАТЕЛЬ
```

Скрипт кратко останавливает процессы записи, сохраняет согласованные БД/файлы и возобновляет те процессы, которые работали. Копируйте зашифрованный результат на другой сервер или в закрытое хранилище. Настройте ежедневный запуск системным cron и хранение не менее 14 дней; скрипт сам не удаляет старые копии. Сбой резервирования должен отслеживаться отдельно.

Восстановление выполняется в распакованную копию проекта **на новом VPS**, без `.env` и без старых volumes:

```bash
bash scripts/restore.sh /path/backup.tar.gz.age /path/family-backup-key.txt --confirm-new-instance
# После проверки DNS, если был Google callback:
docker compose --profile web up -d
```

Restore откажется перезаписывать существующие `.env` и volumes. Он восстановит конфигурацию, БД и оригиналы документов. Если `TOKEN_ENCRYPTION_KEY` потерян, сохранённые Google-токены расшифровать нельзя — потребуется повторная авторизация.

## 8. Локальная разработка

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
DEBUG=1 python manage.py migrate
DEBUG=1 pytest -q
```

Настройки читаются из переменных процесса; локальный Python сам по себе не загружает `.env`. Compose загружает его автоматически. Для локального запуска используйте конфигурацию окружения IDE. Без `DATABASE_URL` допускается SQLite только для разработки; production Compose всегда использует PostgreSQL. Для параллельных worker и полного приёмочного прогона нужен PostgreSQL.
