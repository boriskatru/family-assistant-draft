# Сообщения об ошибках в личном чате

Бот может отправлять техническую диагностику одному из двух разрешённых пользователей. В исходном диалоге остаётся короткое сообщение с кодом ошибки, подробности приходят только в настроенный личный чат. Ошибки фоновых заданий приходят туда же. Включение этой функции не исправляет первопричину сбоя автоматически.

## Настройка

Добавьте в рабочий `.env`:

```dotenv
# Замените 1001 своим личным Telegram ID из /id.
ERROR_ADMIN_TELEGRAM_ID=1001
ERROR_ALERT_COOLDOWN_SECONDS=600
```

`ERROR_ADMIN_TELEGRAM_ID` — один положительный ID пользователя из `ALLOWED_TELEGRAM_IDS`, не ID группы и не список через запятую. Получатель должен открыть бота в личном чате и выполнить `/start`. Пустое значение или `0` отключает личные уведомления об ошибках; безопасная диагностика остаётся в логах.

`ERROR_ALERT_COOLDOWN_SECONDS` задаёт интервал подавления повторов одной причины, по умолчанию 600 секунд. Разные причины могут дать отдельные уведомления. Права и получатель повторно проверяются перед отправкой уже поставленного в очередь отчёта.

После установки версии с этой функцией изменение `.env` применяется командой:

```bash
docker compose up -d
```

Обычный `docker compose restart` не перечитывает переменные окружения контейнера.

## Что приходит

Отчёт содержит код ошибки, этап обработки и класс исключения. Для распознанных ошибок API добавляются HTTP-статус, известный код ошибки, параметр или имя инструмента и краткое объяснение. Для внутреннего сбоя доступны места вызовов в исходниках проекта. Коды позволяют сопоставить ответ в Telegram с логами контейнеров.

Текст пользовательского запроса, адреса, документы, персональный промпт, API-ключи, заголовки запросов и полное тело ответа провайдера не включаются. Неизвестная ошибка может содержать только тип и место возникновения: её причина не подменяется догадкой о неверном API-ключе.

Отчёты подключены к ошибкам основного агентского цикла и его лимитам, неожиданным сбоям инструментов, подготовке вложений, обработке свободного текста, polling, планировщику и workers. Обычные ошибки формата команды и отказы в доступе остаются ответами пользователю. Намеренная остановка агента не считается техническим сбоем.

## Проверка доставки

Отправьте `/start` в личном чате, затем выполните на VPS:

```bash
docker compose exec worker_chat python manage.py shell -c "from assistant.error_reporting import report_error; print(report_error(RuntimeError('diagnostic check'), 'manual.test'))"
```

Команда ставит тестовый отчёт в очередь и печатает его код. Она не создаёт событий и не изменяет адресную книгу. Дождитесь сообщения в личном чате; повтор этой команды в пределах интервала не должен создавать поток одинаковых уведомлений.

Если сообщение не пришло:

```bash
docker compose ps -a
docker compose logs --no-color --since=15m --tail=150 worker_notifications worker_chat bot scheduler
```

Проверьте, что `worker_notifications` запущен, получатель указан в разрешённых пользователях и уже написал боту в личку. Не присылайте полный `.env` или API-ключи для диагностики.

## Когда нужны серверные логи

Ошибки загрузки настроек Django, запуска контейнеров и миграций возникают до запуска обработчиков уведомлений. Например, строка из двух ID в `SHARED_CHAT_ID` остановит запуск: это поле принимает одну группу. Такие сбои проверяйте отдельно:

```bash
docker compose logs --no-color --tail=150 migrate
```

Если PostgreSQL недоступен, отчёт нельзя записать в очередь; останется безопасная запись в логах. Если Telegram или worker отправки недоступны, уведомление не будет мгновенным. Для поставленных в очередь отчётов действуют обычные ограниченные повторы отправки; ошибка доставки самого отчёта не создаёт новый отчёт и не запускает бесконечный цикл.

В старых версиях сообщение «Не удалось завершить агентский цикл» не раскрывает причину, а лог `Agent run failed (...)` сохраняет только класс исключения. По одному такому ответу нельзя отличить отказ API от ошибки SDK, истории диалога или БД. Для диагностики уже случившегося сбоя сначала сохраните текущие логи `worker_chat`, а после обновления воспроизведите запрос. Перед повтором запроса на создание записей проверьте `/agent_history`, `/places` или соответствующие карточки: выполненные действия не откатываются автоматически.

## Окно памяти в 50 сообщений

`AGENT_HISTORY_USER_LIMIT=50` — размер скользящего окна, не количество разрешённых запросов за всё время. В новый запрос входят максимум 49 прошлых сообщений пользователя с ответами и текущий запрос. Старые обмены вытесняются из памяти диалога; сохранённые события, дела и адреса остаются в своих таблицах.

Длина текста и контекст модели ограничиваются отдельно: 50 длинных сообщений могут потребовать больше токенов, чем 50 коротких. Код дополнительно сокращает историю по бюджету `AGENT_MAX_TOTAL_TOKENS`. Отказ API из-за размера контекста будет отражён известным кодом `context_length_exceeded`, если провайдер его вернёт. Само достижение 50 сообщений не должно отключать агента; снижать лимит или стирать историю без диагностики не требуется.
