# ТЗ: семейный ИИ-ассистент в Telegram

Версия 1.1 · 3 ноября 2026 года

## 1. Назначение и границы

Разработать ассистента для Бориса и Анны: личные и общие проекты, дела, расписание, поездки, билеты и списки вещей. Интерфейс — личные чаты с Telegram-ботом и необязательный общий семейный чат.

Размещение — один VPS, Docker Compose. Без n8n и отдельного веб-интерфейса. HTTP-адреса используются только для webhook, авторизации Google и проверки работоспособности. Покупка билетов, бронирование и платежи в объём разработки не входят.

## 2. Возможности и правила

| Область | Требования |
|---|---|
| Общение | Принимать текст, голосовые, PDF и изображения; понимать свободные формулировки и уточнения к предыдущему сообщению. Отвечать на вопросы о сохранённых данных: «что завтра?», «когда следующий созвон?», «что осталось по проекту?» |
| Проекты и дела | Проект: цель, результат, сроки, участники и статус. Задачи и подзадачи: ответственный, статус, приоритет, дедлайн, длительность и зависимости. По запросу ИИ предлагает разложение проекта на дела; после подтверждения сохраняет. Задача может существовать без проекта и назначенного времени |
| События | Встречи, работа, созвоны, мероприятия, поездки; время, место, участники, описание. Событие может относиться к проекту, задаче и поездке; у одной задачи может быть несколько событий |
| Повторения | Календарные серии, сменные циклы (например, 2/2) и задачи через заданный срок после фактического выполнения предыдущей. Исключения: одно вхождение, вся серия либо это и следующие. Каждое повторение дела — отдельная задача |
| Календарь | Подключить Google-аккаунт каждого; выбрать личные календари и один общий. Двусторонняя синхронизация, включая изменения и отмены непосредственно в Google Calendar |
| Напоминания | Несколько напоминаний к событию/дедлайну; настраиваемые интервалы, получатели, тихие часы. Отдельные уведомления о выходе, подготовке, регистрации на рейс. Перенос автоматически пересчитывает связанные уведомления |
| Планирование | Подбирать свободные окна с учётом обоих расписаний, длительности дел, зависимостей, дороги и буферов. Неподвижные события не переносить автоматически. Предлагать план, показывать конфликты и нехватку времени |
| Поездки | Перелёты, поезда, переезды, проживание и мероприятия: адреса, местные времена, пассажиры, бронирования и их статусы. Подготовительные задачи связывать непосредственно с поездкой. Проверять достижимость следующего участка с учётом дороги, регистрации, посадки и багажа |
| Утренний план | Ежедневно в личное время каждого присылать его события и дела, общие обязательства, маршрут, время выхода, нужные вещи и кнопки получения билетов. По умолчанию — 08:00, Europe/Moscow; настройки меняются в чате |
| Билеты | Сохранить оригинал, извлечь дату, маршрут, пассажира и реквизиты; связать с человеком и одним/несколькими событиями. Различать бронь, электронный билет и посадочный талон. Выдавать исходный файл; не генерировать заново QR/штрихкоды |
| Созвоны | Создавать Google Meet для поддерживающего его подключённого календаря; хранить и отправлять ссылку участникам в личные чаты перед началом. Можно вручную сохранить ссылку другого сервиса |
| Вещи | Необязательный список у события или поездки: ввод свободным текстом, выдача и отметки чек-листом в Telegram. Подробности — в разделе 3 |

**Доступ.** Допускаются два заранее разрешённых Telegram ID; каждый запускает бота в личном чате. Видимость задаётся у объекта: `private` — только владелец; `busy_only` — второму доступны лишь время и «занят»; `shared` — оба видят подробности. `busy_only` применяется к событиям, их сериям и поездкам; документы при этом закрыты. Участие, видимость и редактирование независимы: владелец редактирует всегда, второму право выдаётся явно для общего объекта. Участник может предложить изменение через согласование. Общий чат получает только общие данные; занятость без деталей — при отдельном разрешении владельца для этого чата. Связь с общим проектом не расширяет доступ к личным делам и файлам.

**Изменения и автономность.** Однозначную личную команду выполнять сразу с кнопкой отмены; неоднозначность уточнять. Самостоятельно бот предлагает размещение и переносы. В настройках можно разрешить автоматический перенос собственных гибких блоков выбранных категорий в пределах заданных дней/часов. Это не разрешает менять дедлайны, неподвижные встречи и общие договорённости: последние согласуются с затронутыми участниками. Внешние приглашения требуют подтверждения. Повторная доставка команды или нажатия не повторяет действие.

**Категории и обратная связь.** `work/personal` — отдельный признак проектов, задач и событий, не определяющий доступ. У связанных объектов можно наследовать категорию проекта и явно переопределять её. В Telegram различать «сохранено в ассистенте, синхронизация ожидается», «синхронизировано», «ошибка синхронизации»; до успешной записи в БД не отвечать «сохранил».

**Достоверность.** Ответы строить по БД; извлечённые из билета данные подтверждать перед созданием событий. Неизвестные сведения уточнять. Дорогу рассчитывать через адаптер API маршрутов, сохраняя источник и время расчёта; при сбое использовать обозначенную ручную оценку. Стартовую точку пользователь задаёт адресом или добровольно переданной геолокацией.

### 2.1. Персональное планирование

Профиль каждого: рабочие интервалы по дням и исключения, сон, перерывы, домашний/рабочий и другие обычные адреса, предпочтительный транспорт, дневной лимит нагрузки, минимальный блок сосредоточенной работы и буферы. Не смешивать сон и тихие часы уведомлений. Настройки заполняются через чат; неизвестные ограничения уточнять, временные допущения показывать. Не запрашивать весь профиль до первой полезной команды.

Алгоритм дня:

1. Зафиксировать подтверждённые встречи, смены, сон и другие обязательства.
2. Добавить подготовку, дорогу, перерывы и запасы времени; выявить уже существующие конфликты.
3. Вычислить свободные окна и оставшийся лимит нагрузки.
4. Отобрать доступные по зависимостям задачи: сначала просроченные и ближайшие дедлайны, затем приоритет. При равных условиях — раньше созданная задача. Учитывать оставшуюся длительность; делить работу только при разрешении на разделение.
5. Размещать задачи в подходящих окнах; для совместного выполнения брать пересечение доступности обязательных участников. Общая видимость задачи одного исполнителя не занимает время второго. Не помещающиеся дела перечислять с причиной и предложениями, не перегружать день молча.
6. Сохранить версию плана. В личном сообщении разделить обязательные события, предложенные блоки, логистику и проблемы; по настройке отправить в общий чат только совместную часть. Предложенные блоки попадают в календарь после принятия либо по разрешённому правилу автоматизации.

Изменение встречи, завершение дела или сообщение о задержке запускает пересчёт затронутой части дня. Автопереносы выполняются только в разрешённых пределах; существенные изменения присылаются одним кратким сообщением. Расчёт ограничений выполняет код, ИИ объясняет результат и предлагает альтернативы.

### 2.2. Поездки и транспорт

Связать подготовительные дела («страховка», «регистрация», «проверить документы»), участки маршрута, пассажиров и документы. Для бронирования хранить состояния `planned/pending/confirmed/cancelled`; наличие файла не означает подтверждение брони или прохождение регистрации.

Для соседних участков проверять цепочку: окончание предыдущего события → получение багажа/другие процедуры → дорога → регистрация/контроль → посадка. Запасы настраиваются по участку и не считаются универсальной гарантией стыковки. Показать требуемое время, доступное время и дефицит. При переносе обновить связанные напоминания и предложить изменения дальнейшего маршрута.

**Дополнительная опция, отдельно от базовой приёмки:** автоматические задержки/отмены рейсов и транспорта через специального поставщика данных. Нужны договорённость о провайдере, ключ и проверка покрытия. Хранить источник и время обновления; устаревший статус явно обозначать. В базовой версии изменения поступают от пользователя или из календаря.

## 3. Основные сценарии в Telegram

1. **Подключение.** `/start` → проверка пользователя → timezone и время сводки → авторизация Google → выбор календарей. Настройки — `/settings`.
2. **Событие.** «В пятницу в 15:00 встреча по Элкому на час» → определить дату/проект → проверить пересечения → сохранить карточку с кнопками «Перенести», «Отменить», «Билеты», «Вещи».
3. **Дело.** «Оформить страховку до понедельника» → задача. «Найди два часа на доклад» → предложить окна → после выбора создать связанное событие.
4. **Повторения.** «Работа по будням с 9 до 18» → серия. «В эту среду начну в 11» → изменить только указанное вхождение.
5. **Поездка.** Пересланные билеты + «это наша поездка в Японию» → предложить маршрут и участников → подтвердить и сохранить. «Пришли обратные билеты» → отправить оригиналы.
6. **Изменения дня.** «Задерживаюсь на 40 минут» → пересчитать дорогу → показать затронутые события → применить согласованный перенос.
7. **Созвон.** При создании встречи с признаком онлайн бот запрашивает Meet, дожидается готовой ссылки и сохраняет её. В заданное время отправляет ссылку в личные чаты внутренних участников; ошибку создания показывает явно. [4]
8. **Вещи.** «На конференцию взять паспорт, билеты, фотоаппарат и визитки» → сохранить исходный текст и преобразовать в позиции. Для «паспорт каждому» создать отдельные позиции Бориса и Анны; для общего фотоаппарата — одну позицию с ответственным.
9. **Проект и профиль.** «Разложи подготовку доклада к пятнице на шаги; после 20:00 работу не ставь» → предложить задачи и оценки, сохранить ограничение → после принятия подготовить выполнимый план.
10. **После выполнения.** «Менять фильтр через месяц после каждой замены» → создать текущую задачу; после отметки «готово» один раз создать следующую с новой датой.
11. **Доступ.** «Эту встречу показывай Анне только как занятость» → изменить видимость конкретного события; кнопки, поиск, сводки и общие ответы не раскрывают название, адрес или вложения.

Пример сообщения чек-листа:

> **Конференция · Что взять · собрано 1 из 4**  
> ☐ Паспорт — Борис  
> ☐ Билеты  
> ☑ Фотоаппарат — Анна  
> ☐ Визитки — 30 шт.

Под сообщением — inline-кнопки отметки/снятия, «Добавить», «Показать оставшееся»; для длинного списка — страницы. Состояние хранится в БД, копии сообщения обновляются при взаимодействии. Сброс отметок требует подтверждения. Новое повторение события получает свежий список. Необязательный чек-лист включать в подготовительное напоминание и утреннюю сводку. Реализация — обычное сообщение и inline-кнопки Bot API. [1]

## 4. Архитектура и стек

| Слой | Решение |
|---|---|
| Приложение | Python, Django: бизнес-правила, ORM, миграции, внутренние сервисы и HTTP endpoints |
| Telegram | aiogram: сообщения, файлы, кнопки и маршрутизация диалога [2] |
| Данные | PostgreSQL: предметные данные, состояние диалога, задания и журнал отправок |
| ИИ | Один агент-координатор через LLM API; структурированные вызовы разрешённых инструментов. Распознавание речи и документов — отдельные адаптеры |
| Интеграции | Google Calendar/Meet, адаптер маршрутов; провайдеры и ключи задаются конфигурацией |
| Файлы | Закрытый постоянный каталог VPS; доступ через бот. Интерфейс хранилища допускает последующий переход на S3 |
| Развёртывание | Docker Compose: `app`, `worker_chat`, `worker_service`, `scheduler`, `postgres`, `caddy` для HTTPS. Одна кодовая база приложения |

**Поток:** webhook проверяет секрет Telegram и пользователя → одной транзакцией сохраняет update и задание → отвечает Telegram. Worker получает разрешённый контекст, вызывает LLM и сервисные функции. Изменения и задания внешних действий сохраняются транзакционно. Повторный update распознаётся по ID. [1]

Модули: `accounts`, `dialog`, `planning`, `trips`, `checklists`, `documents`, `integrations`, `notifications`. LLM вызывает инструменты `find_events`, `create_task`, `propose_plan`, `attach_file`; код проверяет права, даты и запись. Прямой SQL-доступ и секреты модели не выдаются; инструкции внутри документов не исполняются. Напоминания и выдача сохранённых билетов по кнопке работают без LLM.

**Фоновая работа:** scheduler раз в 30 секунд создаёт задания; worker захватывает их через `SELECT FOR UPDATE SKIP LOCKED`, освобождая транзакцию до сетевого вызова. Предусмотреть аренду с heartbeat, повторы и восстановление просроченной аренды. `worker_chat` обслуживает LLM/OCR, `worker_service` — напоминания и интеграции с отдельным слотом для отправок. Redis/Celery в первой версии не требуются. [7]

**Синхронизация:** PostgreSQL — внутренняя модель, Google Calendar — представление календарных полей. Каждые 2 минуты импортировать изменения через incremental sync; хранить `syncToken`, внешние ID, `etag` и последнюю общую версию. При утрате токена выполнить полный пересмотр, сохранив внутренние связи. Одновременные правки с двух сторон требуют выбора пользователя. [3]

Каждый подключает Google через OAuth с фоновым доступом; refresh token шифруется, одноразовый `state` привязывает callback к пользователю. После отзыва доступа предложить переподключение. Для общего календаря выбрать одно соединение на запись; личные события туда не экспортировать. [5]

## 5. Логическая модель БД

Все предметные сущности: UUID, `created_at`, `updated_at`, версия для проверки конкурентных изменений. Для проектов, задач, событий, серий, поездок и файлов: `owner_id`, `visibility`; допустимые режимы — по разделу 2. Для проектов/задач/событий — независимый `domain`. Ниже — обязательные поля; служебные поля и индексы уточняются в миграциях.

| Таблица | Ключевые поля и связи |
|---|---|
| `users` | `telegram_user_id` unique, `private_chat_id`, имя, IANA timezone, время сводки, тихие часы, разрешение публиковать занятость в общем чате |
| `planning_profiles`, `user_locations` | Профиль 1:1 user: рабочие/сонные интервалы, исключения дат, перерывы, лимит минут нагрузки, минимальный блок, буферы, транспорт, правила автопереноса по категориям/окнам. Адрес: user, название, адрес, координаты; личный по умолчанию |
| `bot_settings` | Единственная запись: разрешённый общий `chat_id`, настройки интеграций без открытых секретов |
| `projects`, `project_members` | Проект: название, цель/ожидаемый результат, описание, даты начала/окончания, domain, статус active/paused/done/archived. Участник: project, user, роль; участие не расширяет видимость дочерних объектов |
| `tasks` | `project_id?`, `trip_id?`, `parent_task_id?`, `recurrence_rule_id?`, `occurrence_key?`, `previous_task_id?`, название, описание, domain, категория, assignee, статус todo/in_progress/done/cancelled, приоритет, дедлайн, оценка/остаток минут, разрешение делить, `completed_at?` |
| `task_participants` | task, user, `required`; уникальная пара. Assignee — ответственный и обязательный участник; дополнительные участники определяют совместную доступность, не видимость |
| `task_dependencies` | `task_id`, `depends_on_task_id`; уникальная пара, запрет циклов |
| `events` | `project_id?`, `task_id?`, `trip_id?`, `recurrence_rule_id?`, `occurrence_key?`, тип, domain, категория, название, начало/конец, timezone начала/конца, all_day и даты, место/координаты, статус proposed/confirmed/cancelled, fixed/flexible, буферы, `meeting_url`, `packing_notes?` |
| `event_participants` | `event_id`, внутренний `user_id` либо внешний email, имя, роль, ответ на приглашение. Уникальность участника в событии; внешний адрес подтверждается пользователем |
| `recurrence_rules` | Вид event/task; режим calendar/cycle/after_completion. Для calendar: DTSTART, timezone, RRULE; для cycle: дата-якорь и шаблон смен/выходных; для after_completion: интервал и единица day/week/month, локальное время срока. Общие: исключения, окончание, шаблоны полей, участников, напоминаний и вещей без отметок. Календарные серии — совместимы с Google Calendar [6] |
| `occurrence_overrides` | `rule_id`, исходный `occurrence_key`, действие cancel/modify, изменённые поля; уникальная пара. Ключ сохраняется после переноса |
| `trips` | `project_id?`, название, даты, описание, статус, `packing_notes?` |
| `trip_participants` | `trip_id`, `user_id`; уникальная пара |
| `trip_segments` | `trip_id`, `event_id` unique, порядок, transport/stay/activity, пункты, перевозчик, номер рейса/брони, booking_status, запасы на регистрацию/посадку/багаж, сроки отмены/регистрации при наличии. Время и timezone — в событии |
| `trip_connections` | Соседние from/to segment, способ перемещения, оценка дороги, дополнительные процедуры/запас, источник и время расчёта, доступные/требуемые минуты, статус feasible/conflict/unknown |
| `files`, `file_links` | Файл: путь, имя, MIME, размер, SHA-256, document_type = reservation/ticket/boarding_pass/other, извлечённый текст, метаданные, `telegram_file_id?`. Связь: file и ровно один FK на событие/задачу/поездку/проект; у файла может быть несколько связей |
| `travelers`, `segment_travelers`, `file_travelers` | Путешественник: имя, `user_id?`; связи M:N с участками и файлами. Для гостей учётная запись не нужна; упоминание пассажира не даёт ему доступ к боту |
| `checklists` | Ровно один FK: `event_id` или `trip_id`, название, исходный текст; права наследуются от родителя |
| `checklist_items` | `checklist_id`, текст, количество, `assignee_id?`, порядок, `checked_at?`, `checked_by?`; личные вещи разных людей — разные позиции |
| `object_editors` | user и ровно один FK на проект/задачу/событие/серию/поездку/файл; уникальная пара объект–user. Владелец имеет право неявно; дополнительный редактор допустим только для shared. Проверки согласования общих изменений сохраняются |
| `daily_plans`, `plan_items` | План: user, местная дата, timezone, версия, статус draft/accepted/superseded. Элемент: plan, task/event либо road/break, интервал, proposed/confirmed, источник, объяснение; снимок не расширяет права на исходные данные |
| `calendar_connections`, `calendar_sources`, `calendar_bindings` | Соединение: пользователь, зашифрованные OAuth-токены. Календарь: connection, внешний ID, роль personal/shared, права записи, собственный syncToken. Связь: source, событие/серия, внешний event ID, etag, последняя общая версия, статус синхронизации |
| `reminders` | Ровно один FK на событие/задачу/поездку, получатель, тип, момент или смещение от выбранной опоры, актуальная версия объекта, статус |
| `jobs`, `deliveries` | Задание: очередь chat/service, тип, приоритет, payload, `run_at`, статус, attempts, `locked_until`, ошибка, `dedup_key` unique. Отправка: job, адресат, message ID, время, результат pending/sent/failed/unknown |
| `dialog_sessions`, `incoming_updates` | Сессия по пользователю и чату: контекст, ожидаемое уточнение/подтверждение, версия объекта, срок действия. Update: уникальный Telegram update ID, данные, состояние обработки |
| `action_requests` | Инициатор, объект/исходная версия, предлагаемые изменения, согласующие и их ответы, срок действия, статус proposed/approved/rejected/applied/expired; применяется однократно, при устаревшей версии требует пересмотра |
| `audit_log` | Кто, когда, что изменил; предыдущие/новые значения, связь с действием и возможность компенсирующей отмены |

**Связи:** проект 1:N задачи; задача 1:N события; поездка 1:N сегменты; сегмент 1:1 событие; событие/поездка 1:N чек-листы; чек-лист 1:N позиции. Проверять FK, согласованность проектов и доступ; ссылки не расширяют видимость документов. Индексы: владелец/статус, время события, дедлайн, `jobs(status, run_at)`; внешние calendar/event ID уникальны в пределах подключения.

**Время и повторения:** моменты хранить в UTC (`timestamptz`), отдельно IANA timezone; all_day — даты с исключающей конечной датой. Календарные серии и сменные циклы вычислять от локального времени с учётом переходов часов и материализовать на 180 дней, расширяя горизонт по запросу. Уникальность `(rule_id, occurrence_key)` предотвращает дубли. «Это и следующие» разделяет серию; история завершённых дел сохраняется.

Для `after_completion` будущую цепочку заранее не создавать: завершение текущего дела транзакционно создаёт ровно одного преемника, unique `(rule_id, previous_task_id)`. Срок — completed_at плюс календарный интервал в timezone правила; для отсутствующего числа месяца брать последний день месяца. Повторное «готово» не сдвигает срок. Отмена завершения отменяет ещё не начатого преемника; если он уже изменён/начат, требуется разрешить конфликт. После отмены и нового завершения восстанавливать того же отменённого преемника с пересчитанным сроком, не создавать дубль. Сменный цикл хранить отдельно от RRULE; в Google экспортировать совместимые серии либо конкретные события с внешними ID.

## 6. Надёжность и эксплуатация

1. Перед отправкой проверять актуальную версию события и права; устаревшие напоминания отменять. Временные ошибки повторять с задержкой и учётом лимитов API.
2. После рестарта отправлять актуальные уведомления, просроченные до 15 минут; остальные включать в сводку пропущенного. «Пора выходить» после начала события не отправлять. Утренний план — один на пользователя/местную дату, догоняющее окно 3 часа.
3. Неопределённый результат отправки фиксировать; критичное напоминание можно повторить с пометкой. Абсолютное отсутствие дублей при потере ответа Telegram не гарантируется.
4. Секреты — вне репозитория; токены зашифрованы. БД и файлы закрыты извне. Проверять права на каждом действии; исключить секреты и билеты из логов.
5. Ежедневно резервировать БД и файлы вне VPS в зашифрованном виде на 14 дней; предусмотреть восстановление ключей. Мониторить ошибки, диск и доступность внешней проверкой.
6. Стартовый ориентир VPS: 2 vCPU, 4 ГБ RAM, 40 ГБ SSD при внешнем LLM; уточнить нагрузочным прогоном. Зафиксировать зависимости. Настройки — в Telegram, эксплуатация — CLI.

## 7. Приёмка и результат разработки

1. Оба пользователя создают личные и общие дела/события; посторонний Telegram ID доступа не получает. Личное содержание и файлы не раскрываются супругу или общему чату, включая ответы ИИ.
2. Создание события в боте и ручной перенос в Google Calendar синхронизируются без дубля; при доступных API изменение появляется в боте не позднее 5 минут. Одновременные правки вызывают разрешение конфликта.
3. Перенос одного повторения сохраняет остальные. Сценарий «это и следующие», смена часового пояса и перелёт через полночь дают правильные даты и напоминания.
4. После рестарта сохраняются задания, оригиналы билетов и отметки вещей. При исправных API напоминание передаётся Telegram не позднее 60 секунд после срока; получение на устройстве зависит от Telegram и связи.
5. Каждый получает свой утренний план с делами, дорогой, общими событиями и нужными вещами. Конфликт встреч и недостаточное время на дорогу явно показываются.
6. Загруженный билет находится по поездке/событию и отправляется исходным файлом. Дубликат вложения не создаёт повторного события. Ссылка Meet создаётся либо возвращается понятная ошибка; её рассылка работает без участия LLM.
7. Текстовый список вещей превращается в чек-лист. Отметка, снятие, ответственный, количество и разделение «каждому» сохраняются; повторный callback не меняет состояние второй раз. Новое повторение события получает незаполненный список.
8. Общий перенос проходит согласование; отмена действия восстанавливает предыдущее состояние, если запись с тех пор не менялась. Повторная доставка Telegram update не повторяет изменение.
9. План учитывает сон, рабочие окна, перерывы, лимит нагрузки и зависимости; лишние дела остаются в явном списке. Предложенный блок не становится подтверждённым без принятия или разрешённого правила. Видимая обоим задача одного исполнителя не блокирует время второго; совместная задача учитывает обязательных участников.
10. Для 2/2 правильно строятся смены; «через месяц после выполнения» создаёт одного преемника от фактической даты, включая конец месяца и повторное нажатие «готово».
11. `busy_only` скрывает название, место и документы во всех ответах; просмотр общего события не даёт права менять его. Категория work/personal не меняет доступ.
12. Проект раскладывается на дела после подтверждения. Подготовительная задача находится по поездке, даже без проекта. Билет и посадочный талон различаются и находятся для нужного пассажира/участка.
13. Невыполнимая стыковка выявляется с указанием дефицита. Автоперенос затрагивает только разрешённые личные гибкие блоки; обязательные/общие события сохраняют правила согласования. Пользователь видит фактическое состояние записи и синхронизации.

Передать репозиторий, миграции БД, Docker Compose, `.env.example`, инструкцию запуска/подключения Google/резервирования и автотесты критичных сценариев выше. Порядок реализации: основа и календари → напоминания/билеты/чек-листы → поездки, логистика и планирование. Всё перечисленное входит в итоговый объём, кроме явно выделенной опции автоматического получения транспортных задержек.
